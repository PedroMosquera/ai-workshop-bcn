# AI workshop decks

Browser slide decks for an AI workshop, served by GitHub Pages from `main` (repo root). Each deck is written as one markdown file in `decks/` and built into one self-contained HTML file by `build.py`. On every push to `main` the `Build decks` workflow rebuilds the HTML, tests it and commits it, and Pages republishes the site in about a minute.

Read this before changing anything. The goal is that every edit, by a person or an agent, matches what is already here.

## Files

| File | What it is |
|---|---|
| `index.html` | Landing page linking the decks. Small, no embedded assets. Edited by hand. |
| `decks/build.md` | Source of the parking-app build brief: agenda, checkpoints, status board, demos. |
| `decks/playbook.md` | Source of "A way of working with AI": CLAUDE.md, spec, journal, commands, guards, habits. |
| `decks/README.md` | The markdown syntax for slides, cards, tags, code blocks and row layouts. |
| `build.html`, `playbook.html` | The built decks. Generated by `build.py`: never edit them by hand. |
| `build.py` | Turns `decks/*.md` into the HTML decks. Python 3.9+, no packages. |
| `template/` | Shared page (`deck.html`), deck-only CSS and JS (`build.*`, `playbook.*`), status board, logo, fonts and images. |
| `tests/` | Syntax tests and a check that each HTML deck matches its markdown. |
| `.github/workflows/build-decks.yml` | Rebuilds, tests, fit-checks and commits the decks; comments preview links on pull requests. |
| `tools/fit-check.sh` | Checks every slide fits its viewport (4 sizes x 2 themes). Run it before every push. |
| `tools/fit-check.html` | The in-browser checker the script drives. |

## How the decks were made

They were generated with Claude Code using the `dt-slides` skill (Dynatrace Corporate 2026 style, from the internal AI knowledgebase repo, `plugins/dt-slides`), then edited by hand, and later converted to the markdown sources in `decks/`. The skill is not needed to edit them: everything it produced is already in `template/`. Use it only if you build a new deck from scratch, and then add it as a new `decks/*.md` on the shared template so the decks stay identical in behaviour.

## Edit the markdown, not the HTML

`build.html` and `playbook.html` are about 800 KB each, almost all of it base64 fonts and images, and they are rebuilt from `decks/*.md` on every change. Read and edit the markdown instead. Never paste the built HTML's base64 lines into a prompt or a diff review.

- Slides start at `=== slide` lines, labelled by the `<!-- NN NAME -->` comment above: `grep -n '<!-- ' decks/build.md`.
- CSS sections start at `/* === NAME === */`: `grep -n '/\* === ' template/deck.html`.

## Anatomy of a deck

In order inside `template/deck.html`, the page every deck is built on:

1. `FONTS`: DTFlow `@font-face` rules, inlined from `template/assets/` as base64 at build time (weights 100, 300, 500, 600, 700). Do not touch.
2. `THEME TOKENS`: every colour, as CSS variables on `:root` (dark) and `[data-theme="light"]`. The only place colours are defined.
3. `VIEWPORT BASE`: from the skill's `viewport-base.css`. Slides are exactly one screen tall; sizes use `clamp()` and `rem`, and the root font size grows with the window on large screens.
4. Component CSS (`BASE`, `TITLE`, `CHECKPOINT`, `STATUS BOARD`, `BRAND CHROME`, ...). CSS only one deck uses lives in `template/<deck>.css`.
5. Slides: built from `decks/*.md` into `<section class="slide">` > `<div class="slide-content">` plus `<aside class="notes">` for speaker notes (`Notes:` in the markdown).
6. `PRESENTATION CONTROLLER`: keyboard, nav dots, pager, theme toggle, notes panel, `?slide=N`.
7. `build.html` only: `STATUS BOARD` in `template/build.js` and `template/board.html` (5 teams x 4 checkpoints, saved in the presenting browser's localStorage).

## Style rules

- **Colours only through tokens**: `var(--teal)`, `--blue`, `--purple`, `--pink`, their `-text` variants, `--text`, `--text-2`, `--text-3`, `--card`, `--card-border`. Never a hex value in a slide or new CSS. Palette: teal `#49C2B3`, sky `#3BACF0`, blue `#1966FF`, purple `#5E28E5`, magenta `#8D1CDC`, pink `#C93FDB`, navy `#1A2440`. Nothing outside it.
- **Meaning of colours**: teal = done / build time / primary highlight; blue = in progress / info; purple = checkpoints; pink = need help / warnings. Keep it consistent with the status board.
- **Both themes must work.** Check every change in dark and light (press T).
- **Type**: DTFlow. Headings 500, body 300, emphasis (`<strong>`) 600. Code and labels use JetBrains Mono.
- **Logo and backgrounds**: the logo sits top-left (white) in dark and bottom-left (colour) in light; background images appear only on the first and last slide, only in dark. Handled by `BRAND CHROME`; do not add more.
- **One screen per slide, no scrolling.** At most: a heading plus 4-6 bullets, or up to 6 cards, or 8-10 lines of code. More content means a new slide.
- **Text**: plain English, short sentences. No emoji anywhere (use inline SVG for icons). No em or en dashes. Fake data only, no real names.

## Building blocks to reuse

Reuse these classes instead of writing new CSS. Most have a markdown shortcut (`^` eyebrow, `>` lede, `::: card accent-g`, `[[b: tag]]`, `- [ ]` checklist, row lists for the agenda and checkpoint track): see `decks/README.md`.

- Layout: `cols-2`, `cols-3`, `cols-4`, `grid`, `cp-layout` (`cp-left` / `cp-right`), `meta-row`.
- Text: `eyebrow` (small mono label above a heading), `lede` (intro paragraph), `small`, highlights `.g` `.b` `.o`.
- Cards: `card` plus an accent border `accent-g` (teal), `accent-b` (blue), `accent-v` (purple), `accent-o` (pink).
- Tags: `tag`, `tag b`, `tag v`, `tag o` (same colour order as the accents).
- Lists: `checklist` (with `<span class="box"></span>`), `bullet-list`.
- Timeline: `agenda` + `agenda-bar` (the evening), `cp-track` + `cp-step` (checkpoint overview).
- Motion: `reveal` on a single element, `stagger` on a container whose children appear one by one.

The class names `g` / `v` / `o` predate the current palette (they meant green, violet, orange). They now map to teal, purple and pink. Keep using them; do not rename.

## Keeping the schedule consistent

Clock times appear in several places in `decks/build.md`. When one changes, change all of them in the same commit:

- the agenda slide (`02 THE EVENING`) rows and the `agenda-bar` column widths in `template/build.css` (one `fr` per minute, one column per row),
- the checkpoint overview (`cp-track`),
- each checkpoint slide's time tag,
- the pit stop, demos and closing slides,
- the speaker notes on those slides.

Find them with `grep -n -E '1[78]:[0-9]{2}' decks/build.md`.

## Adding or moving a slide

- Copy the nearest similar `=== slide` block in the markdown and keep its structure.
- Inserting or removing a slide shifts every later slide number, so `?slide=N` links shared earlier will point one slide off. Say so in the commit message.
- New teams or checkpoints on the board: change `StatusBoard.TEAMS` / `CHECKPOINTS` in `template/build.js` and the table header in `template/board.html` together. A size change resets saved board state, which is intended.

## Before you push

1. `python3 build.py` and `python3 -m unittest discover -t . -s tests` must pass. The workflow runs them and the fit check below too, but run them before pushing: the fit check reads the built HTML.
2. `tools/fit-check.sh` must print only `ok` lines and end with `sanity: planted overflow detected`. It needs Google Chrome and python3 (set `CHROME` if Chrome is not in `/Applications`).
3. Open the deck locally, step through the slides you touched in both themes, and open the notes panel (N).
4. No em or en dashes in added lines: `git diff | perl -CS -ne 'print if /^\+.*[\x{2013}\x{2014}]/'` must print nothing.
5. Commit messages say what changed and why. No AI co-author trailers or "generated with" footers.
